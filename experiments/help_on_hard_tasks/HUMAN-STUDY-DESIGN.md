# 从本轮预试验到真人研究

本轮已完成工程验收、任务筛选和开放助手代理求助的观察；实际未产生问题或代理答复。未招募真人，也没有比较过真人背景的帮助效果。自然问题包见 [空包说明](QUESTIONS.md)。

## 要回答的三个问题

1. 模型遇到可见障碍时，会不会问一个具体、有用的问题？统计全部任务轨迹，保留没有问题的运行。
2. 不同经验的人能否理解、回答这个问题？分别记录 Lean 经验、相关算法／数学知识、一般编程经验，不能只按学历或年级分组。
3. 模型能否采用并核验答复，克服原障碍？区分“答复正确”“模型采用”“局部障碍解决”和“整个任务得分提高”。

本轮强求助指导与 ask_user 同时存在，因此只能观察这个条件下是否提问。不能由本轮推断无指导时的行为，也不能从某条 help 比 solo 得分高直接得出帮助的因果效果。

## 后续材料与流程（待实施）

- 从真正发生的 ask_user 提取问题原文、提问时公开代码与错误、已执行尝试、剩余模型预算。保留来源 entry 与删节记录，不给参与者看后来的答案或终末评分。
- 先检查材料是否足以让人理解。缺少上下文要标出来；不能研究者补写一个更好的问题后仍称为原问题。
- 使用 [记录表](HUMAN-STUDY-FORM.md) 收集背景、答复、自信、投入时间及验证方式；背景维度分别分析，样本少时以案例和描述结果为主。
- 对“哪类回答者更有帮助”的正式比较，让不同背景者面对匹配的问题状态、可见资料、回答时间和模型剩余预算；若采用同状态答复分支，明确这是答复效果实验，不能冒充独立全任务运行。
- 将无法回答、不正确建议、模型未采用、验证失败等结果保留下来。回答者帮忙定位验证命令、发现需求歧义或纠正方法，也可能有价值，不把帮助限定为写完整证明。

真实招募、同意流程、样本量、分组／随机化以及数据保存范围应在开始真人研究前固定。未来若先用助手代理答复试跑，不能算入真人组；本轮没有实际代理答复。

一个待检验的后续方向是：让模型看到帮助者真实、具体的能力说明，例如其 Lean 经验和相关数学／算法经验，观察是否改变求助选择。不能虚构专家身份，也不能由本轮未提问就断言“模型不知道帮助者的优势”是根因。能力说明对提问意愿的作用，与实际答复质量对解题的作用，应分别研究。

## 基础设施前置条件

后续正式研究先确保提供商的 token 限流不会主导任务结果，并明确服务重试时间如何计入预算。本轮保留固定参数与所有失败证据，不事后补时间或挑选成功重跑。若未来修改预算口径、并发、模型或输出容量，作为新的实验条件重新冻结。
